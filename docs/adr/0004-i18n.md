# ADR 0004: internacionalização da UI

Status: aceito.

## Contexto

O Flutter usa `slang` com inglês (`en`) como locale base e traduções para `pt-BR` e `es`. O app Rust já persiste a preferência de locale, mas a UI ainda mantém textos em `crates/app/src/labels.rs`. A paridade exige que texto apresentado ao usuário não fique espalhado no código da interface e que erros do domínio continuem tipados, sem frases traduzidas no core.

## Decisão

Usar **Project Fluent**, pela crate `fluent-bundle`, para as mensagens da interface. Os catálogos ficam no crate da UI, em `crates/app/locales/{en,pt-BR,es}.ftl`; a crate `gsh-core` não depende de i18n.

Os IDs das mensagens são estáveis, em kebab-case e agrupados pelo domínio/tela, por exemplo `gsh-workspace-empty-title` e `settings-language-label`. O texto traduzido e valores interpolados ficam nos catálogos Fluent. A UI resolve os IDs pelo locale atual; strings de apresentação não são montadas por concatenação nem escritas como frases literais nos widgets.

A resolução usa a preferência salva quando definida; caso contrário, tenta o locale do sistema entre os suportados. Locale ausente ou não suportado usa `en`. A lista suportada nesta etapa é `en`, `pt-BR` e `es`.

Erros continuam como enums tipados nas crates de domínio. A camada de UI converte cada variante para uma mensagem Fluent e fornece os argumentos necessários, sem colocar a frase localizada na crate de domínio.

## Consequências

- Fluent cobre argumentos e pluralização sem implementar regras de plural manualmente.
- Cada catálogo precisa conter os mesmos IDs; testes devem detectar IDs ausentes ou extras entre os três locales.
- A migração de `labels.rs` e das mensagens restantes acontece junto com a implementação das telas, preservando os IDs por domínio/tela.
- `fluent-bundle` e o tipo de locale entram como dependências diretas quando a camada de carregamento dos catálogos for implementada; não se depende de crates transitivas de `iced`.
